# IntentFlow Dashboard 前端风格重构方案

> 依据：项目当前 Dashboard 页面与样式、P6–P8 运维边界，以及用户提供的 Binance 前端设计拆解。本文定义后续实现方向，不代表页面已经完成重构。

## 1. 产品定位

IntentFlow Dashboard 是面向开发者和运维人员的本地只读控制台，用于查看已保存的 Runtime 与流动性池快照、Intent 执行证据、交易结果和验收进度。它读取本地 SQLite 证据，不发起交易、签名或链上写入；页面数据代表已持久化记录，不应表现成实时链上行情。

重构目标是让用户更快判断“数据是否可用、最近运行到哪里、某笔执行发生了什么、验收还缺什么”，同时减少无意义装饰并提升表格和长标识符的可读性。

### 设计原则

- 借鉴 Binance 的信息分层、紧凑排版、低装饰表面、数字对齐和明确状态反馈。
- 保留 IntentFlow / Portaldot 自身识别，不复用 Binance 标识、专有字体或整套品牌色。
- 继续以浅色界面为默认。当前使用场景以长时间阅读证据和状态表格为主，没有必须改为深色终端的依据。
- 颜色表达品牌或数据状态，不用作大面积装饰。成功、失败、警告和未知状态必须有文字标签，不能只靠颜色区分。
- 视觉变化不得暗示产品尚不具备的实时行情、自动刷新、可执行交易或已通过验收。

## 2. 当前页面基线

当前页面由以下区域组成，建议保留信息架构和数据语义：

| 区域 | 当前内容 | 重构方向 |
| --- | --- | --- |
| 顶栏 | IntentFlow 品牌、更新时间、节点浏览器链接、手动刷新 | 保持单行优先；窄屏允许换行；刷新状态清楚可见 |
| 页面标题 | “运行面板”、本地证据库状态 | 建立页面标题与数据库状态的主次关系 |
| 运行摘要 | 最新运行、池快照、执行证据、本地模拟耗时 | 保留四项并列摘要；数值使用等宽数字，说明文本降低强调 |
| Runtime 与流动性池 | 区块快照表 | 提高表头、地址、资产、储备和区块列的扫描效率 |
| Intent 与交易证据 | 可筛选的证据表及行详情 | 让状态、Intent、交易 hash 和结果容易比较；长数据按需横向查看 |
| 验收报告 | 生成命令与测试网交易、部署、性能样本进度 | 保持未采集、缺项等真实状态，不将本地数据包装成链上验收结果 |
| 页脚 | 只读边界说明 | 继续保留并保持清晰可读 |

当前实现已经有明确的浅色底、品牌绿、细分割线、表格和移动端断点，重构重点是统一语义 Token、状态样式、数字排版和各屏宽度下的阅读秩序，而不是推倒重做。

### 需要在实现时一并核对的界面问题

- 绿色目前同时承担品牌标识、主按钮和成功状态。品牌绿应留给品牌与主操作，成功状态改用独立的语义色，避免含义混淆。
- 执行状态由数据动态生成 CSS class，但当前样式只明确覆盖 `confirmed` 和 `rejected`。实现时应为已确认、待处理、失败和未知状态建立显式映射，并展示可读标签。
- 搜索框提示包含 `route`，但当前筛选逻辑实际只匹配 Intent、route hash 和交易 hash。界面文案应准确描述当前可搜索字段；若扩大搜索范围，应另行修改并核对筛选逻辑。
- 证据行目前通过鼠标点击打开详情。重构详情交互时，应补齐键盘焦点和 Enter / Space 操作，避免 hover 样式成为唯一线索。
- API 暂不可用时，页面会更新数据库状态，但表格仍保留空数据文案。后续实现可区分加载、空数据、筛选无结果和读取失败状态，且不得将这些状态混为一谈。

## 3. 视觉方向

目标风格为“清晰、克制、可核验的链上运维台”：页面背景承担整体空间，白色表面承载表格和摘要，细边框负责分区，绿色仅突出品牌和主要操作。整体密度可以接近金融终端，但保留足够行高和留白，确保长 hash、错误原因和中文标签都能阅读。

不建议引入 Binance 黄色作为 IntentFlow 品牌色，也不建议为追求交易终端观感而采用全黑背景、行情闪烁、大面积红绿色块、玻璃质感或卡片阴影。当前产品没有 K 线、订单簿或实时推送，不需要为了风格增加这些视觉暗示。

### 色彩 Token 建议

以下颜色从项目现有样式出发整理为语义变量；最终对比度应在页面实现后逐项核对。

```css
:root {
  color-scheme: light;

  --color-canvas: #f5f7f6;
  --color-surface: #ffffff;
  --color-surface-subtle: #f7f9f8;
  --color-surface-selected: #f1f6f3;

  --color-text: #202b33;
  --color-text-muted: #68767b;
  --color-text-quiet: #728083;

  --color-border: #dce3e0;
  --color-border-soft: #e8edeb;

  --color-brand: #147352;
  --color-brand-hover: #0e6043;
  --color-focus: #218760;

  --color-success: #17623f;
  --color-success-soft: #e1f2e9;
  --color-warning: #805b13;
  --color-warning-soft: #fff3d6;
  --color-danger: #922f2b;
  --color-danger-soft: #fae8e6;

  --shadow-overlay: 0 8px 24px rgb(0 0 0 / 18%);
}
```

普通面板不使用阴影，通过背景和边框建立层级；`--shadow-overlay` 只用于将来确有需要的菜单或浮层。当前若没有浮层组件，不必增加相关样式。

### 字体与数字

- UI 字体建议：`Inter, "Noto Sans SC", "Microsoft YaHei", "PingFang SC", system-ui, sans-serif`。不要依赖未随项目提供或未确认授权的 Binance 字体文件。
- 正文基准 14px；辅助信息 12px；表格可用 12–13px，但触控和窄屏阅读不能因此变得拥挤。
- 页面标题建议 24px 左右，模块标题 16–18px；以字重和间距建立层级，不把每个标题都加粗到最高级。
- 计数、区块号、金额及耗时启用 `font-variant-numeric: tabular-nums`；hash 和机器标识使用本地等宽字体栈。
- 保持字距为默认值，不用压缩字距来制造“金融终端”观感。

### 间距与形状

采用 4px 基础步进：4、8、12、16、24、32、48px。表格单元格优先 8–12px 垂直与水平内边距；摘要项和详情区优先 12–16px；主要区块之间使用 24–32px。

组件圆角统一在 4–6px 范围；按钮、输入框和面板使用同一套尺度。避免圆角胶囊和套叠卡片。边框为 1px 低对比度细线，悬停只提高轻微背景对比。

## 4. 页面与组件规范

### 顶栏和页面标题

- 顶栏维持白色表面和底部分隔线，品牌区固定在左侧，更新时间和操作在右侧。
- 主按钮继续使用项目品牌绿；刷新进行中时禁用按钮并显示清晰反馈，不模拟持续实时刷新。
- 页面标题使用普通工作台标题尺度，不引入营销式 Hero、渐变背景或大图。
- 数据库状态使用“已连接 · 只读”“尚未创建”“暂不可读取”等明确文案；可加小型状态标记，但状态文案必须保留。

### 运行摘要

- 四项指标作为一组横向摘要，桌面端等宽；以细分隔线分开，不在每项外再套一张卡片。
- 标签和说明使用次级文字；主要数值使用 20–24px 中等字重和等宽数字。
- “未采集”与 `--` 是不同含义：未采集是数据状态，`--` 是不适用或无数值；最终实现中统一约定，不以零替代未知。
- `0 / 10` 等验收数字保留当前真实口径，不用装饰性进度条暗示已经完成验收。

### 表格与证据详情

- 表头采用浅次级背景、12px 左右中等字重和稳定高度；正文行以细分割线分隔，使用 tabular numbers。
- 地址和 hash 使用等宽字体、单行省略或首尾缩略；完整值仍应能在详情区域读取或复制。不要在窄列中逐字符换行。
- 行悬停只用于提示可打开详情；键盘聚焦需有与悬停同样清晰的视觉反馈。
- 详情区按“Intent / Route / 执行 / Receipt / 事件 / 风险”分组，长 JSON 保持可换行、可横向浏览，不让内容撑破页面。
- 列表中的状态优先展示短标签；成功、失败、待处理、未提交及未知状态各有独立语义样式，并同时保留文字。
- 表格在窄屏允许横向滚动。保留可见的列标题和稳定行高，避免强行压缩 hash 或将所有列改成难以扫描的卡片。

### 搜索、按钮和空状态

- 搜索框标签和占位文案说明实际支持的字段；焦点边框清楚，输入尺寸不随内容变化。
- 按钮桌面端高度建议 36–40px，移动端至少 40px；禁用态需同时降低视觉强调并保持可读。
- 空状态区分“暂无证据”“没有匹配结果”“数据库尚未创建”“读取失败”。空状态只说明当前状态，不提供虚构的填充数据。
- 错误和风险文本允许换行；hash、路径和长资产标识使用专门的断行规则，不能覆盖相邻内容。

## 5. 响应式行为

保留当前约 820px 和 540px 的主要断点，按内容需要微调，不按设备型号硬编码。

| 视口 | 布局建议 |
| --- | --- |
| ≥ 1200px | 主内容最大宽度约 1440px；摘要四列；验收说明与进度并排；池表与证据表使用完整列布局 |
| 821–1199px | 收窄页面左右留白；摘要保留四列直到数值不可读，再切换为两列；表格可单独横向滚动 |
| 541–820px | 摘要两列；验收区域上下排列；标题和搜索控件允许换行 |
| ≤ 540px | 页面边距约 12px；标题、状态和搜索纵向排列；摘要两列；详情两列或单列；长表在自身容器滚动 |

最窄 320px 时，文本、按钮和输入框不得相互覆盖。关键操作可换行，但不应因按钮文字或 hover 状态改变布局宽度。

## 6. 交互与无障碍

- 悬停、按下、聚焦、禁用和加载状态均要有稳定反馈；键盘焦点使用 `:focus-visible`，不能只靠颜色差异表达。
- 动效控制在 120–180ms，限于背景、边框或轻微淡入；响应 `prefers-reduced-motion`。
- 当前数据通过手动刷新读取本地 API，因此不使用行情 tick 闪烁、持续跳动数字或“在线实时”指示。
- 正文与背景满足 WCAG AA 常规文字对比度目标；状态徽标、边框和焦点指示也要在最终配色下核验。
- 表格可交互行应使用适合键盘操作的语义与事件处理；若仅做样式而不调整语义，应在范围说明中记录该项仍未完成。

## 7. 后续实现顺序

1. 在 `apps/dashboard/public/styles.css` 中建立语义 Token、统一字体/数字规则、间距与组件状态。
2. 按本方案调整顶栏、摘要、区块标题、表格、详情和移动端规则；优先复用现有 HTML 类名和数据区域。
3. 如需键盘行交互、明确的加载/失败空状态或状态标签映射，再小范围调整 `apps/dashboard/public/index.html` 与 `app.js`。这类调整只改善界面语义与反馈，不改变后端数据和链上行为。
4. 页面结构稳定后，在桌面、平板、手机和 320px 窄屏检查实际内容、长 hash、空库、失败状态及键盘焦点。

`apps/dashboard/server.mjs` 的只读 SQLite 行为、loopback 监听与 API 契约不属于视觉重构范围。也不新增行情图表、WebSocket、暗色主题、外部字体或图标依赖，除非后续产品需求明确提出。

## 8. 完成标准

- 品牌色与成功/失败状态色职责明确，未知状态可识别。
- 首屏能快速读出数据库状态、最新运行和验收进度；真实数据与未采集状态没有混淆。
- 表格、数字、hash 和详情在桌面及窄屏均有稳定层级；移动端滚动不会导致页面整体横向溢出。
- 空数据、筛选无结果、数据库缺失和 API 不可用有不同提示。
- 主要控件具备键盘焦点状态，证据详情可由键盘打开。
- 没有引入币安品牌资产、未授权字体、装饰性行情效果，或暗示本地快照是实时链状态的内容。

## 9. 参考范围
