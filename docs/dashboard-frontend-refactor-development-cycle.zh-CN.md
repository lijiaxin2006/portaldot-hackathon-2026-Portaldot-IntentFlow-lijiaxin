# IntentFlow Dashboard 前端风格重构开发周期

> 本文是基于《IntentFlow Dashboard 前端风格重构方案》的实施计划。它描述建议的开发节奏和验收门槛，不代表重构代码已经完成。

## 1. 周期结论

### 推荐周期

在现有页面结构和 API 契约不变的前提下，建议安排 **8 个前端工作日，约 2 个自然周**：

- 1 名前端开发负责实现与自检。
- 1 名产品或设计负责人在关键里程碑进行短评审。
- 后端只需保持 `/api/overview`、证据数据字段和只读服务行为稳定，不需要为视觉重构开发新接口。

如果需要同时补充真实链上数据、改造后端数据模型、增加暗色主题或引入图表库，周期应重新估算；这些内容不在本计划基线内。

### 目标结果

完成后，Dashboard 应具备以下特征：

- 首屏可以快速判断本地证据库是否可用、最近运行到哪里、验收还缺什么。
- 摘要、表格和详情统一使用低装饰、高信息密度的运维台风格。
- 品牌绿、成功、失败、警告和未知状态职责分离。
- 长 hash、区块号、金额、耗时和错误原因在桌面及窄屏均可读。
- 空库、加载中、筛选无结果和 API 失败不会被误显示成真实业务结果。
- 证据详情可通过鼠标和键盘打开，页面不触发交易、签名或链上写入。

## 2. 交付范围

### 本次包含

| 范围 | 目标文件 | 说明 |
| --- | --- | --- |
| 设计 Token 与基础样式 | `apps/dashboard/public/styles.css` | 颜色、字体、数字、间距、边框、状态和响应式规则 |
| 页面语义微调 | `apps/dashboard/public/index.html` | 仅在需要时补充状态容器、键盘语义和准确的字段说明 |
| 数据呈现与交互 | `apps/dashboard/public/app.js` | 状态映射、空状态、错误状态、搜索文案和详情键盘交互 |
| 方案与周期文档 | `docs/` | 记录设计依据、开发顺序和验收标准 |

### 本次不包含

- `apps/dashboard/server.mjs` 的 API 契约、SQLite 查询和 loopback 监听变更。
- 交易签名、广播、Solver、Executor 或合约逻辑改造。
- WebSocket、实时行情、K 线、订单簿、自动刷新和新增图表。
- Binance 品牌资产、Binance 专有字体或其黄色品牌体系的直接复制。
- 新增前端框架、打包器、组件库或外部图标依赖。

## 3. 分阶段计划

### P0：基线确认与任务冻结（第 0.5 天）

**目标**：把当前页面作为可比较基线，确认重构不会改变业务数据含义。

**工作内容**：

- 记录桌面端、平板端、手机端和 320px 窄屏的当前布局问题。
- 核对 `index.html` 的区域、ID 和 `app.js` 的数据字段对应关系。
- 确认 API 仍为只读，空数据库和缺少证据时的现有表现。
- 冻结本轮范围：只改善视觉层、交互语义和状态反馈。

**交付物**：基线问题清单、字段与页面区域映射、变更范围确认。

**通过条件**：产品负责人确认页面仍以“本地只读证据面板”为定位，未将 Binance 交易终端作为页面目标。

### P1：设计 Token 与 CSS 基础层（第 1 天）

**目标**：先统一颜色、字体、数字和空间规则，降低后续局部样式互相覆盖的风险。

**工作内容**：

- 建立 `--color-*` 语义变量和品牌/状态色职责。
- 统一 `font-family`、正文层级、等宽数字和 hash 字体栈。
- 固定 4px 间距步进、4–6px 圆角、1px 低对比度边框。
- 保留浅色主题和现有绿色识别，不引入暗色主题或渐变。
- 统一 `:focus-visible`、禁用态、悬停态和 `prefers-reduced-motion` 基础规则。

**交付物**：可独立审阅的 Token 和基础 CSS diff。

**通过条件**：旧页面的主要区域仍能显示；没有出现未定义变量、全局选择器意外覆盖或文字对比度明显下降。

### P2：顶栏、页面标题与运行摘要（第 2 天）

**目标**：建立首屏的优先级，让用户先读到数据库状态、最新运行和核心计数。

**工作内容**：

- 调整顶栏品牌区、更新时间、节点浏览器链接和刷新按钮的层级。
- 统一页面标题、眉题和数据库状态文案的字号与间距。
- 将四项运行摘要处理为一组稳定的等宽指标，不增加套叠卡片。
- 区分“未采集”“无数据”和“不适用”，不以 `0` 替代未知。

**交付物**：桌面端首屏样式、摘要区域的空数据和正常数据状态。

**里程碑 M1**：第 2 天结束进行一次视觉评审，确认颜色、字体、密度和页面标题层级。

### P3：池快照与证据表格（第 3–4 天）

**目标**：把高密度数据变成稳定、可比较、可横向浏览的表格。

**工作内容**：

- 规范表头、行高、分割线、数值对齐和可交互行的悬停/聚焦反馈。
- 为地址、route hash、交易 hash 和长资产标识建立缩略与完整值查看规则。
- 将执行状态映射为已确认、待处理、失败、未提交和未知等可读标签。
- 保留详情中的 Intent、Route、Receipt、事件和风险信息，不改变数据字段含义。
- 让长错误原因、事件原文和风险 JSON 在详情区域可换行或横向查看。

**交付物**：池快照表、证据表、证据详情的桌面端完成版本。

**通过条件**：使用空库、单条证据、多条证据、长 hash 和失败记录时，表格没有内容重叠，状态文字与数据一致。

### P4：状态语义与交互可访问性（第 5 天）

**目标**：补齐当前页面容易混淆的状态和键盘操作。

**工作内容**：

- 分离加载中、数据库缺失、API 失败、暂无数据和筛选无结果文案。
- 确认搜索框占位提示与实际匹配字段一致；若只支持 hash，文案不写成泛化的 route 搜索。
- 为可打开详情的证据行补充键盘焦点和 Enter / Space 操作。
- 检查按钮、输入框、链接和详情区域的焦点顺序与可读名称。
- 检查状态不只依赖颜色，必要时同时显示文本和辅助信息。

**交付物**：状态矩阵、键盘交互版本、可访问性问题清单及修复结果。

**里程碑 M2**：第 5 天结束完成一次交互评审；所有关键状态至少有一种真实数据或可控空状态可复现。

### P5：响应式与窄屏适配（第 6 天）

**目标**：让信息密度在不同宽度下保持可读，而不是简单缩小桌面页面。

**工作内容**：

- 按 ≥1200px、821–1199px、541–820px、≤540px 四档检查布局。
- 保留摘要两列/四列切换、验收区域上下排列和标题搜索控件换行行为。
- 让证据表在自身容器横向滚动，避免整个页面被长表撑宽。
- 检查 320px 下按钮、输入框、状态文案和详情字段不互相覆盖。
- 检查文本换行、hash 缩略、表头可见性和滚动定位。

**交付物**：四档视口适配结果、窄屏问题清单和修复记录。

### P6：集成核对与静态质量检查（第 7 天）

**目标**：确认视觉重构没有改变数据流、只读边界或页面已有能力。

**工作内容**：

- 核对 `refresh()` 仍从 `/api/overview` 读取，刷新按钮仍为手动触发。
- 核对池、运行、部署、证据、事件和性能字段展示没有被误删或改义。
- 静态检查 HTML 结构、CSS 变量引用、JS 选择器和状态 class 对应关系。
- 检查页面没有新增写接口、密钥读取、签名、广播或外部资源依赖。
- 检查 Git diff 只涉及约定的前端文件和文档，不覆盖工作区已有改动。

**交付物**：候选版本、静态检查记录、已知问题清单。

**里程碑 M3**：第 7 天结束形成候选发布版本；未解决问题按阻塞、可延期和观察项分类。

### P7：验收与交接（第 8 天）

**目标**：让后续维护者可以按文档继续开发，不把“视觉完成”误写成“链上验收完成”。

**工作内容**：

- 按完成标准逐项确认颜色职责、信息层级、状态语义、响应式和键盘交互。
- 使用当前可用证据库验证正常数据、空库、缺失库、失败 API 和筛选无结果。
- 记录尚未具备真实数据的场景，明确其显示为未采集或不可用。
- 更新文档中的实际变更文件、剩余风险和后续建议。

**交付物**：验收清单、变更摘要、剩余风险、交接说明。

**通过条件**：产品负责人确认视觉和交互目标；工程负责人确认只读数据边界和 API 契约未被改变。

## 5. 依赖与前置条件

- `apps/dashboard/server.mjs` 可按现有方式启动，且 `/api/overview` 返回字段保持稳定。
- 至少准备一份空数据库或缺失数据库场景；如果暂时没有真实证据，页面必须按“未采集”验收，不能用假数据代替。
- 评审人员在 M1、M2 和 P7 提供反馈；超过一个工作日未反馈会顺延对应阶段。
- 目标浏览器至少包括当前桌面 Chromium、移动 Chromium 和项目实际支持的中文系统字体环境。
- 不依赖 Binance Nova、Binance Plex 等未随项目提供或未确认授权的字体文件。

## 6. 风险与处理

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 证据字段或状态值继续增加 | 状态颜色和标签出现未知映射 | 统一回退为“未知”，并保留原始值供详情查看 |
| hash、事件和错误文本长度变化 | 表格撑宽或内容重叠 | 表格容器滚动，详情区域允许换行和横向查看 |
| CSS 变量与旧选择器混用 | 局部样式不一致 | P1 先建立 Token，再按区域迁移，避免同时大范围重命名 |
| 空库与 API 失败被混为一类 | 运维人员误判数据状态 | P4 建立状态矩阵，分别核对文案和视觉样式 |
| 追求 Binance 观感导致范围膨胀 | 周期延长并引入错误产品暗示 | 将图表、实时推送、暗色主题和交易控件列为明确范围外 |
| 工作区已有未提交改动 | 误覆盖用户资产 | 每个阶段只触碰约定文件，提交前复核 `git status` 和 diff |

## 7. 验收清单

### 视觉

- [ ] 页面背景、面板、边框和文字层级清楚，没有大面积装饰性阴影或渐变。
- [ ] 品牌绿只承担品牌与主操作，成功、失败、警告和未知状态有独立语义色。
- [ ] 正文、表格、数字和 hash 的字重、行高和对齐规则稳定。
- [ ] 摘要、表格、详情和验收区域没有套叠卡片或不必要的视觉噪音。

### 数据与交互

- [ ] 手动刷新仍只读取本地只读 API。
- [ ] 正常数据、空数据、筛选无结果、数据库缺失和 API 失败显示不同状态。
- [ ] Intent、route hash、交易 hash、区块、事件和风险信息仍可追踪。
- [ ] 证据行可通过键盘聚焦并打开详情；焦点不会被 hover 规则覆盖。

### 响应式

- [ ] ≥1200px、821–1199px、541–820px、≤540px 四档布局通过检查。
- [ ] 320px 视口下没有文字、按钮、输入框和状态标签重叠。
- [ ] 长表只在表格容器横向滚动，不造成页面整体不可控溢出。

### 边界

- [ ] 未新增交易、签名、广播、密钥读取或写入接口。
- [ ] 未把本地模拟、未采集记录或失败记录表述为测试网验收完成。
- [ ] 实际改动文件与本周期范围一致，已有工作区改动未被覆盖。

## 8. 交付后维护节奏

首个版本上线后，建议用一个工作日收集真实使用反馈，重点观察证据表筛选、长 hash、失败原因和移动端横向滚动。后续新增状态或字段时，先更新状态矩阵与 Token，再修改 `app.js` 和样式；不要直接为单个数据值增加临时颜色或局部布局例外。

本周期完成的是 Dashboard 前端风格与交互层重构，不能替代 P8 测试网交易数量、部署记录、runtime 探测或性能样本等链上验收条件。
